Renderer review and implementation plan — 2026-11-04

Recommendation: retain the existing native Wayland EGL/OpenGL renderer. There is evidence of avoidable work worth investigating, but no new benchmark establishing an incremental performance gain. Start with a bounded profiling experiment and ship a change only if it passes the criteria below. A WebGPU migration is not justified by the evidence available.

This is an analysis and proposed implementation plan. No application, renderer, dependency, launcher, or installed-package changes were made. Reviewed repository HEAD: `bd0ccd65fce9c71031f0a200e737a0cc93338044`; renderer commit: `075e650`.

The current implementation already removes the major presentation bottleneck: it keeps the EGL/Skia context and framebuffer wrapper between frames, resizes without recreating the context, submits without an explicit CPU wait, and presents through a child Wayland surface without reading the completed frame into a Swing bitmap. Popups receive the same treatment. Input remains on JBR's parent surface, and renderer failure can fall back to software. These are useful properties to preserve.

The existing [installed Flatpak diagnostic](../2026-11-03-wayland-egl/scroll-summary.json) reports paint median/p95 of 11.169/22.934 ms and EDT queue median/p95 of 14.353/38.435 ms after EGL, versus 23.799/33.079 ms and 35.673/53.519 ms before it. That is one instrumented run per mode on a 419-stroke page. It establishes the original improvement; it does not identify today's remaining bottleneck, quantify GPU completion time, or measure displayed FPS or physical input latency. Pre-EGL cache hit counts must not be treated as a post-EGL profile.

| Candidate | Evidence and likely benefit | Decision |
| --- | --- | --- |
| Reduce CPU ink rasterization during scrolling | `SegmentedInkRasterCache` keys entries by the exact viewport, affine transform and scale. A new scroll position can require a new CPU raster surface and a new image for GPU drawing. | Highest potential application-level candidate; profile the accelerated app, then compare existing vector replay with the raster cache. |
| Pace render requests to Wayland | The bridge requests swap interval zero and implements no application frame-callback scheduler. This leaves a possible opportunity to avoid work for frames that are never displayed. AWT, EGL or the compositor may already limit production. | Measure submitted/presented/discarded updates first. Implement only if excess work or cadence problems are observed. |
| Enable Skiko's existing Swing pacing property | Supported by the installed library, but its Linux clock requires the AWT display refresh rate. The installed JBR Wayland device inherits a method returning refresh rate zero. | A property-only change is ineffective for this inspected runtime. |
| Cache reflection and avoid repeated popup-tree restacking | The renderer resolves peer methods and scans the peer map each draw; restacking walks the component tree and sends stacking requests each frame. | Smaller candidate. Change only if phase timing shows a material cost. Keep peer/surface recreation and popup reordering correct. |
| GPU-backed ink cache or spatial tiles | Could retain useful content across views and avoid CPU raster/image uploads. Requires resource ownership, invalidation and pixel-correct composition work. | Defer until the simpler replay experiment and profile establish a need. |
| Native Vulkan renderer | The current Skiko jar exposes low-level Vulkan context/target bindings, but its Linux Swing factory still creates the OpenGL renderer. A Wayland Vulkan swapchain, synchronization and lifecycle implementation would be additional work. | No demonstrated benefit for this workload; defer. |
| WebGPU via Dawn/Graphite | No Dawn/Graphite context or recorder API is exposed in the inspected Skiko AWT jar. This would require new bindings/builds and integration beyond replacing EGL. | Do not start a custom backend migration. Revisit when upstream provides a supported Linux/JVM path and app profiling supports it. |

The relevant source is [WaylandRenderer.java](../../../desktopApp/src/main/java/com/vivenotes/desktop/rendering/WaylandRenderer.java), [WaylandRendering.java](../../../desktopApp/src/main/java/com/vivenotes/desktop/rendering/WaylandRendering.java), [wayland_egl.c](../../../desktopApp/src/main/native/wayland_egl.c), and [SegmentedInkRasterCache.kt](../../../shared/src/jvmMain/kotlin/com/vivenotes/ui/canvas/SegmentedInkRasterCache.kt). The CPU cache's `Surface.makeRasterN32Premul` call is separate from EGL presentation. Changing presentation API alone will not move this work to the GPU.

Dawn can run natively and wrap Vulkan, Metal, D3D12 or OpenGL; using it does not require embedding a browser. That makes WebGPU technically possible, but does not make it an automatic performance improvement. [Dawn's project description](https://dawn.googlesource.com/dawn/+/HEAD/README.md) documents those backends. A Skia route would require compatible Graphite context/recording APIs, whose model differs from this renderer's Ganesh `DirectContext`; see Skia's [Context API](https://github.com/google/skia/blob/main/include/gpu/graphite/Context.h). The conclusion here concerns this project's Linux/JVM integration, not Graphite support on every Skiko platform.

Upstream releases checked on November 4 list Skiko 0.156.1 and 0.157.0-alpha01 beyond the project's 0.156.0; neither release notes advertise a replacement Wayland/WebGPU Swing renderer. A dependency bump alone is not an established solution. [Skiko releases](https://github.com/JetBrains/skiko/releases). The [GLX-to-EGL PR](https://github.com/JetBrains/skiko/pull/1274) remains open. The separate [native Linux SkiaLayer PR](https://github.com/JetBrains/skiko/pull/1224) is for Kotlin/Native Linux targets and is not a direct replacement for this JVM Swing host.

The pacing limitation was checked against actual binaries, rather than inferred from release notes. The installed Flatpak is still `b758a14aae07a7fc1311c3c67f7a8c6301d281fd212bc232e16fedd1648cbc5a`; its JBR modules match the staged runtime and its Skiko AWT jar matches the Gradle jar inspected. `WLGraphicsDevice` does not override `GraphicsDevice.getDisplayMode()`. The inherited implementation constructs `DisplayMode` with refresh rate zero. Skiko rejects that rate, and both its Linux DRM clock selection and timer fallback need a positive period. Thus even `skiko.swing.frame.pacing.forceTimer=true` does not supply the missing rate. See [static-evidence.txt](static-evidence.txt). Upstream documents the opt-in property and unknown-refresh limitation in the [pacing PR](https://github.com/JetBrains/skiko/pull/1282) and [Compose release notes](https://github.com/JetBrains/compose-multiplatform/releases/tag/v1.13.0-beta01).

Implementation should proceed in this order, with each later step dependent on the evidence from the previous one:

1. **Establish a repeatable baseline on the existing GPU path.** Turn the saved `memory/flatpak-scroll-probes/ScrollProbe.java` investigation into a maintained benchmark using generated representative fixtures and disposable copies when comparing the real notebook. Cover idle, continuous scroll/pan, zoom, pen drawing, erasing, resize and popup animation. Include sparse, 419-stroke-scale and dense pages. Keep logical bounds, actual buffer dimensions, zoom, notebook contents and input timing constant between candidates. Record repository/artifact hashes, actual renderer, JBR, GPU/driver and compositor. Run at least five paired fresh-process comparisons, alternating order after warmup, at scale 1, 1.5 and 2 where available. Use the real compositor/GPU for performance; headless tests establish correctness only.

   Instrument separately: peer/geometry lookup, Compose/Skia drawing, ink cache builds, GPU submission, EGL swap, and EDT queue delay. Measure CPU use, retained and peak working memory, cache hits/builds, and frame intervals. Use asynchronous GPU timers where supported; do not insert `glFinish` or per-frame readback. Collect timing runs with minimal instrumentation and separate sampled profiles to locate costs. Schedule input independently of EDT completion and record actual delivery, rather than slowing the input producer with `invokeAndWait` as the old diagnostic did.

   For actual presentation evidence, optionally collect `wp_presentation` feedback for owned child surfaces; it distinguishes presented and discarded content updates and reports presentation timestamps. Frame callbacks alone are scheduling hints, not proof that a frame was displayed. Account for the protocol's clock before comparing timestamps. [Presentation protocol](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/stable/presentation-time/presentation-time.xml). If this optional protocol is unavailable, report that limitation instead of relabeling swap timings as display latency.

2. **Test the dominant avoidable cost with one small candidate.** If CPU ink raster construction and image transfer account for a substantial part of scroll cost, first add a benchmark-only policy that replays the existing retained ink paths into the normal Compose/Skia drawing commands for changing views. Compare that with the current viewport raster cache on the same EGL renderer. Keep stationary-view reuse and the software path available. This tests whether avoiding the intermediate CPU image helps without introducing a new graphics API or cache architecture. Direct vector replay can also be slower on complex pages, so it must win the real workload comparisons before becoming normal behavior.

   If the winning profile still warrants offscreen GPU caching, design that as a separate follow-up: surfaces/images must belong to the active `DirectContext`, carry a context-generation key and be released on context loss, hide/dispose and backend changes. The jar exposes `Canvas.recordingContext` and `Surface.makeRenderTarget`, but Compose can provide a recording canvas without a GPU context during draw-command recording. Probe that capability at the actual call site; do not assume a nullable accessor is a reliable GPU cache factory or store images across popup contexts. Keep the existing memory bound explicit and account for temporary surfaces and duplicate uploaded textures. Spatial tiles also need seam, fractional-transform and invalidation tests; they are not the first implementation step.

3. **Add native frame scheduling only if the baseline proves it useful.** When redundant submissions or inconsistent cadence are material, prototype a gate in the rendering adapter using `wl_surface.frame` on owned EGL child surfaces. Present the first needed frame promptly, coalesce later invalidations to the newest state, and allow resize/expose and show transitions to recover correctly. Keep input handling independent. Do not block the EDT waiting for a callback, sleep on the EDT, or simply switch to a blocking swap interval.

   Callback delivery must continue when no new frame is being drawn. Today's native queue is dispatched only from `present()`, so waiting for a callback without an independent event pump would stall rendering. Give the callback queue a correct shared-display read/dispatch lifecycle, following libwayland's prepare/read/cancel requirements; the existing touch reader demonstrates the pattern. Marshal notifications to the EDT without drawing from the reader thread. Never consume JBR's default queue. Cancel outstanding callbacks on hide/dispose/failure and use a bounded recovery path for missing callbacks without creating an idle repaint loop. Keep this scheduler as the sole added pacing mechanism. [Wayland frame protocol](https://wayland.freedesktop.org/docs/html/apa.html#protocol-spec-wl_surface-request-frame).

4. **Handle bridge overhead only if it is large enough to matter.** If lookup/restacking costs are visible in the profile, cache reflective method handles by peer type, refresh the actual peer/surface binding when it changes, and update stacking on hierarchy/order/visibility changes instead of every frame. Preserve nested popup disposal's saved EGL binding restoration. Do not combine context-sharing, render-thread migration, buffer-age damage rendering or fractional-resolution changes into this patch. Each changes correctness assumptions and needs separate evidence.

5. **Validate and apply a predeclared acceptance rule.** Proposed performance bar: at least a repeatable 15% reduction in p95 frame/EDT delay, or a 20% reduction in active CPU/energy at equivalent displayed cadence, with no material pen-input latency, visual, idle-use or memory regression. These are decision thresholds, not predicted results. Judge the distribution across paired runs, not the best run; investigate regressions on other workloads before accepting a candidate. If no candidate clears the bar, retain the current implementation and record the result.

   Add deterministic scheduler tests for immediate/continuous invalidations, callback loss, nested popup close, visibility and disposal, and software fallback. Preserve the strict existing CPU cache/reference tests. Add GPU image comparisons for overlaps, alpha, erasing/undo, selected/live strokes, fractional scroll/zoom and clipping, and UI tests for continued input and popup interaction. Do not loosen existing assertions to accommodate a candidate. Run focused tests, the full JVM suite, and `:desktopApp:nativeWaylandTest` with DISPLAY unset at scales 1 and 2 plus fractional-scale compositor coverage. Require native cases to execute rather than silently skip. Verify real compositor screenshots, context reuse, bounded resources and failure fallback. Finally repeat the benchmark on the packaged Flatpak artifact, not just Gradle classes.

Reconsider Vulkan or WebGPU only if profiling after these steps shows GPU/driver command processing is the remaining material cost, or an upstream supported backend removes the custom adapter at comparable performance. Then compare an isolated alternate backend against EGL with the same fixtures and acceptance criteria. There is no evidence here supporting the cost of maintaining a Skiko/Skia/Dawn fork now.

Review validation: source inspection, upstream primary-source research, installed/staged binary hashes and bytecode inspection. No new runtime benchmark or automated test suite was run for this analysis-only change; historical test reports are not a new verification of current HEAD.


Implementation outcome — 2026-11-04

Steps1 and2 are implemented and validated. The default native GPU path replays ink during changing
views and retains stationary raster reuse/software fallback. The predeclared queue-tail bar passed
in all15 host pairs and5 actual-bundle pairs. See [implementation.md](implementation.md) for measured
results, CPU/latency limits, current tests and artifact identity. Steps3/4 were conditional and are
deferred: no presentation evidence supports pacing, and bridge lookup/restacking cost was small.
The complete JVM/native checks and actual exported Flatpak comparison in step5 passed. No
installation, Git commit or publication was requested/performed.
